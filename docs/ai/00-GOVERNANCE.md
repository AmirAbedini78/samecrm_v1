# 00 — قرارداد و سازوکار مستندات هوشمند (Governance)

این سند «قانون اساسی» مستندات پروژه است.  
هدف: داکیومنت *خودش را گسترش بدهد* بدون اینکه تبدیل به یک فایل شلوغ و غیرقابل نگهداری شود.

---

## 1) چهار نوع سند (و اینکه کجا بنویسیم)

### A) Governance (همین فایل)
وقتی **قراردادها/روال‌ها/نام‌گذاری‌ها** عوض می‌شود.

### B) Project Map (`01-PROJECT-MAP.md`)
وقتی **تصویر کلی** پروژه تغییر می‌کند: ماژول‌ها، ساختار پوشه‌ها، جریان‌های اصلی داده، استانداردهای مهم.

### C) Domain Docs (`02-domains/*.md`)
وقتی تغییر مربوط به یک **فیچر/دامنه مشخص** است (باگ، توسعه، ریفکتور، UI، تنظیمات).

### D) ADR (`03-adr/*.md`)
وقتی یک تصمیم «قابل بحث/برگشت» یا «دارای اثر طولانی» می‌گیرید:  
مثلاً انتخاب محل ذخیرهٔ تنظیمات، نحوهٔ scope کردن CSS، الگوی مسیردهی، معماری سرویس‌ها، و…

---

## 2) تاکسونومی Scope (نام‌گذاری استاندارد)

هر بخش داکیومنت باید یک بلوک Scope داشته باشد تا AI فقط همان قسمت را بخواند/آپدیت کند.

**فرمت پیشنهادی:**
- Domain/Product: `crm | leads | customers | deals | tickets | inventory | reports | settings | theme`
- Layer/Tech: `backend | frontend | database | api | jobs | auth | permissions`
- Cross-cutting: `custom-styling | performance | security | logging | testing`

**نمونه Scope:**
Scope: inventory, belzona, frontend, custom-styling, datatable

---

## 3) Definition of Done (چرخهٔ اجباری هر تسک)

برای هر تسک، این 5 قدم باید انجام شود:

1) تشخیص Scope تسک (۳ تا ۷ کلیدواژه از تاکسونومی)
2) خواندن فقط بخش‌های مرتبط
3) اعمال تغییر در کد
4) ثبت تغییر در داکیومنت دامنه (History entry)
5) اگر تصمیم معماری بود → ثبت یک ADR

---

## 4) قالب‌های استاندارد

### قالب History Entry (داخل Domain Doc)
- تاریخ: `YYYY-MM-DD`
- خلاصهٔ تسک: یک جمله
- فایل‌های کلیدی: ۳ تا ۷ مسیر
- تغییر رفتار: قبل/بعد (کوتاه)
- نکته/هشدار: یک خط

### قالب ADR
- Context (مسئله)
- Decision (تصمیم)
- Alternatives (گزینه‌های بررسی‌شده)
- Consequences (اثرها/ریسک‌ها)
- References (فایل‌ها/PR/کامیت‌ها)

---

## 5) ضدالگوها (کارهایی که ممنوع است)

- گذاشتن کدهای طولانی داخل داکیومنت (فقط مسیر فایل + توضیح)
- ریختن همه چیز در یک فایل بزرگ
- تاریخچهٔ بدون «چرا» (چراها باید ADR شوند)

---

## 6) پروتکل هوشمندی: Dependency Resolver (برای Cursor/AI)

هدف این پروتکل این است که **کاربر فقط نام ماژول را بگوید** و AI خودش:
- فایل ماژول را از `02-domains/INDEX.yml` پیدا کند
- وابستگی‌های `reads` و `depends_on` را **بازگشتی** (recursive) دنبال کند
- وضعیت فعلی کد/معماری را از روی مستندات صحت‌سنجی کند
- تسک را انجام دهد
- و در پایان، مستندات را آپدیت کند

### الگوریتم (الزامی)
1) ورودی: نام ماژول/فیچر (مثلاً «انبار بلزونا») + شرح تسک
2) در `02-domains/INDEX.yml` مسیر فایل را پیدا کن
3) فایل ماژول را بخوان و Frontmatter آن را استخراج کن
4) همهٔ آیتم‌های `reads` و `depends_on` را جمع کن و برای هرکدام دوباره مرحله 3 را اجرا کن (تا جایی که آیتم جدیدی اضافه نشود)
5) خروجی بده:
   - Current State Summary (وضعیت فعلی)
   - Risk & Traps (ریسک‌ها/تله‌ها)
   - Touch Points (فایل‌های کدی که احتمالاً باید تغییر کنند)
   - Smoke Checks (چک‌های سریع بعد از تغییر)
6) سپس تسک را اجرا کن
7) در پایان:
   - History entry استاندارد در فایل ماژول اضافه کن
   - اگر تصمیم معماری ایجاد شد/تغییر کرد → ADR بساز/آپدیت کن
   - اگر وابستگی جدید کشف شد → `depends_on` ماژول را آپدیت کن
   - اگر تغییر سراسری بود → `01-PROJECT-MAP.md` را هم آپدیت کن

### “Prompt Macro” پیشنهادی برای استفاده در Cursor
کافی است کاربر این الگو را استفاده کند:

> می‌خوام «{نام ماژول}» رو تغییر بدم: {شرح تسک}  
> طبق پروتکل Dependency Resolver، از `02-domains/INDEX.yml` ماژول رو پیدا کن، فایلش و همهٔ `reads/depends_on` رو بازگشتی بخون، وضعیت فعلی رو خلاصه کن، بعد تغییر رو انجام بده و در پایان History/ADR/depends_on را آپدیت کن.

## 7) سیاست دو‌زبانه (Bilingual Documentation Policy)

هدف: توضیحات برای انسان (فارسی) راحت باشد، اما **شناسه‌های فنی و ساختار برای AI/ابزارها (انگلیسی)** دقیق و بدون ابهام بماند.

### قواعد ثابت
- کلیدهای Frontmatter **همیشه انگلیسی** باشند:  
  `id, title, type, reads, depends_on, touches_code, smoke_checks, validation_queries, update_rules, aliases`
- `id/module_id` همیشه **انگلیسی و kebab-case** باشد.  
  مثال: `inventory-belzona`, `shared-custom-styling`
- نام فایل‌های داکیومنت **انگلیسی** باشد (داخل `aliases` نام فارسی هم اضافه شود).
- متن بدنهٔ توضیحات **فارسی** است، اما:
  - مسیر فایل‌ها، نام کلاس‌ها/متدها/routeها/جدول‌ها/کلیدهای config **دقیقاً همان چیزی باشد که در کد هست** (انگلیسی).
  - اصطلاحات فنی را انگلیسی بنویس تا ambiguity کم شود (مثلاً: `Scoped CSS`, `Service Layer`, `Repository`, `Middleware`, `Policy`, `Migration`, `Seeder`, `Validation`, `Mismatch`).

### واژه‌های مرجع (Canonical Terms)
برای یکسان‌سازی:
- اسکوپ CSS = `Scoped CSS`
- تزریق CSS = `CSS injection`
- صحت‌سنجی = `Validation`
- عدم‌تطابق داکیومنت با کد = `Mismatch`
- گسترش پیشرونده = `Progressive Expansion`

> اگر در متن فارسی یک اصطلاح چندپهلو شد، نسخهٔ انگلیسی‌اش را کنار آن بیاور.
